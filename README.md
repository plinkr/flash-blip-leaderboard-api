# FLASH-BLIP Leaderboard API

Backend server for receiving, managing, validating replays, and storing high scores for the game [FLASH-BLIP](https://github.com/plinkr/flash-blip).

Developed as a personal hobby project, it is currently actively used as the backend API for the game's leaderboard. Its main purpose is to serve as a foundation so other developers can implement their own leaderboard system, simply adapting the replay validator and physics engine to their own game mechanics.

It is written in Go using the Fiber v2 framework and persists data in PostgreSQL. It features a two-phase security pipeline (HMAC handshake) and an asynchronous physics simulation engine to verify game replay integrity before confirming entries on the leaderboard.

## Key Features

- **Challenge-Response Handshake**: Two-step score submission protocol using temporary single-use UUID tokens and HMAC-SHA256 signatures.
- **Anti-Cheat Replay Validation**:
  - *Synchronous phase (Light)*: Immediate analysis of tick ordering, event rate limits (BLIPs/PINGs per minute), and binary header validation.
  - *Asynchronous phase (Physics Simulation)*: Deterministic game replay (jump physics `playerY`, height bonuses, multipliers, and difficulty curve) for entries qualifying for the Top N.
- **V1 and V2 Replay Support**: Compatible with the legacy V1 binary format and the V2 specification with validation header (`FBRP`) and explicit multiplier events.
- **LZ4 Compression**: Decompression of the event stream generated by the LOVE2D client.
- **User-Agent Filtering**: Configurable restriction for authorized clients (default `LuaSocket 3.1.0`).
- **Nonce Cleanup & Maintenance**: Request deduplication and background automatic purge of expired tokens and nonces.
- **Community Moderation**: Score reporting system with auto-invalidation upon reaching the configured threshold.

## Prerequisites

- **Go**: Version 1.26 or higher.
- **PostgreSQL**: Version 15 or higher.
- **Development Environment**: Developed and tested natively on Linux.
- **Docker and Docker Compose** *(Optional)*: For containerized deployment.

## Configuration and Environment Variables

The server reads environment variables from the system or from a `.env` file in the project root. You can refer to `.env.example` and `internal/config/config.go`.

| Variable | Description | Default Value |
| :--- | :--- | :--- |
| `PORT` | HTTP server listening port | `8080` (`.env.example`) |
| `DATABASE_URL` | PostgreSQL connection string | `postgres://postgres:postgres@localhost:5432/flash-blip-leaderboard?sslmode=disable` |
| `RATE_LIMIT_RPM` | Requests per minute limit per IP on critical endpoints | `5` |
| `LEADERBOARD_DEPTH` | Number of Top positions to validate and display | `100` |
| `ALLOWED_USER_AGENTS` | Comma-separated list of authorized User-Agents | `LuaSocket 3.1.0` |
| `ALLOWED_ORIGINS` | Allowed origins for CORS | `*` |
| `TIMESTAMP_SKEW_SECONDS` | Allowed timestamp skew margin in seconds | `60` |

## Installation and Building from Source

1. Clone the repository and navigate into the project directory:
   ```bash
   git clone https://github.com/plinkr/flash-blip-leaderboard-api
   cd flash-blip-leaderboard-api
   ```

2. Download and install Go dependencies:
   ```bash
   go mod download
   ```

3. Build the binary for the target architecture:

   - **Linux x86-64**:
     ```bash
     GOOS=linux GOARCH=amd64 go build -ldflags="-s -w" -o flash-blip-leaderboard-api-backend.bin ./cmd/server/main.go
     ```

   - **Raspberry Pi (ARM64 / armv8)**:
     ```bash
     GOOS=linux GOARCH=arm64 go build -ldflags="-s -w" -o flash-blip-leaderboard-api-backend-rpi.bin ./cmd/server/main.go
     ```

4. Run database migrations and start the server:
   ```bash
   ./flash-blip-leaderboard-api-backend.bin
   ```
   *Note: On startup, the server automatically executes the SQL migrations located in `internal/db/migrations/001_init.sql`.*

## Deployment with Docker and Docker Compose

The repository includes a two-stage `Dockerfile` (static compilation on `golang:alpine` and execution on `scratch`) and a `docker-compose.yml` file that spins up PostgreSQL 15 alongside the application.

To start the entire infrastructure with Docker:

```bash
docker compose up --build -d
```

This will run:
- A PostgreSQL container (`leaderboard_db`) on port `5432` with healthcheck.
- The backend API container (`leaderboard_app`) on port `8080` once the database is ready.

To stop the services:
```bash
docker compose down
```

## Security Architecture

Score submission is not done via a simple direct HTTP POST request, but requires a validation protocol:

```
[Game Client]                         [Backend Server]                      [PostgreSQL]
       |                                      |                                  |
       |--- 1. POST /scores/prepare --------->|                                  |
       |    (Metadata: score, ticks, etc)     | Generates Token (30s) & Nonce    |
       |<--- Returns { token, nonce } --------|                                  |
       |                                      |                                  |
       | Compresses Replay (LZ4)              |                                  |
       | Signs HMAC-SHA256(Body, key=Nonce)   |                                  |
       |                                      |                                  |
       |--- 2. POST /scores/submit ---------->|                                  |
       |    Headers: X-Submit-Token,          | Verifies Token + HMAC Signature  |
       |             X-Signature              | Consumes Token (single use)      |
       |                                      | Decompresses LZ4 & Parses (V1/V2)|
       |                                      | Synchronous Light Validation     |
       |                                      |--- Stores Score + Replay ------->|
       |<--- Returns { ok, score_id } --------| (Score in Pending state)         |
       |                                      |                                  |
       |                                      | [Async Goroutine]                |
       |                                      | Is it within Top N?              |
       |                                      | Simulates Replay (Physics+Ticks) |
       |                                      | Compares Claimed vs Simulated    |
       |                                      |--- Marks Validated True/False -->|
```

### Score Submission Protocol
1. **Preparation (`POST /scores/prepare`)**: The client sends match metadata (`p`, `s`, `total_ticks`, `replay_version`, `rng_seed`, `difficulty`). The server temporarily stores the session in memory and returns a unique `token` (UUID) and a cryptographic `nonce` valid for 30 seconds.
2. **Signing and Submission (`POST /scores/submit`)**: The client prepends a 4-byte prefix (little-endian) with the uncompressed size, compresses the binary input stream with LZ4 (LOVE2D block format), and encodes the result in Base64. Next, it calculates the HMAC-SHA256 signature using the `nonce` as the secret key over the Base64 body and submits it with `X-Submit-Token` and `X-Signature` headers.
3. **Token Consumption**: The server validates the token, verifies the HMAC signature in constant time, and marks the token as consumed to prevent replay attacks or race conditions.

### Replay Validation Levels
- **Synchronous Validation (Light)**: Decompresses the LZ4 stream and inspects the replay structure (`ParseReplay`). Checks monotonic tick ordering, ensures input count does not exceed human frequency limits (maximum BLIPs/PINGs per minute), and in V2 validates multiplier sequences and the `FBRP` binary header.
- **Asynchronous Validation (Physics Simulation)**: If the score is a candidate for the Top N (`LEADERBOARD_DEPTH`), `validator.SimulateReplay` runs asynchronously:
  - Simulates player vertical trajectory (`playerY`), scroll speed, height bonus accumulation, and difficulty progression.
  - Generates dynamic tolerance bounds (`ToleranceLow` and `ToleranceHigh`).
  - If the claimed score falls within the simulated range, the entry is marked as `validated = true`. Otherwise, it is rejected (`validated = false`) with the reason logged.
- **Pending Replay Sweeper**: A periodic process (`RunPendingReplaySweeper`) checks unvalidated pending entries qualifying for the Top N to process them in the background.
- **Community Moderation**: The `POST /scores/:id/report` endpoint allows users to report scores. Upon reaching 3 or more reports, the server automatically invalidates the score.

## API Endpoints

### Public
- `GET /health`: Server health status.
- `GET /scores`: Returns top validated scores within the Top N.
- `GET /scores/check/:score` | `POST /scores/check`: Checks if a score would qualify for the Top N (accepts value as path parameter, query parameter `?score=`, or JSON body `{"score": 1234}`).
- `GET /replays/:id`: Downloads compressed replay binary data along with metadata in HTTP headers (`X-Replay-Seed`, `X-Replay-Version`, `X-Replay-Ticks`, `X-Replay-Difficulty`).

### Score Submission (Protected)
- `POST /scores/prepare`: Initiates handshake and generates session token/nonce.
- `POST /scores/submit`: Submits signed replay for processing.

### Moderation
- `POST /scores/:id/report`: Registers a report against a score.
